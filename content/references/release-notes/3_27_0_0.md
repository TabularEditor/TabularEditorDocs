## New in 3.27.0.0

Check out our [release blog](https://blog.tabulareditor.com/) to get a brief overview of the most important updates in this release.

### MCP Server

Tabular Editor 3 can now act as an **MCP (Model Context Protocol) server**, which means the agent harness you already use (Claude Code, GitHub Copilot, VS Code agent mode, Codex, Cursor and others) can drive the same features as the AI Assistant against the model you have open. If you have been curious about agentic semantic model development but did not want to set up another AI subscription, or you simply prefer working in your own agent, this is the way in.

What the agent works on is the model **as it stands in front of you in Tabular Editor**: your unsaved edits included, through the same object model, the same C# scripting engine and the same safety checks the AI Assistant uses. Everything the agent does lands in your Tabular Editor session, where you can inspect it, undo it and save it when you are happy with it.

Choose **Tools > MCP Server...** and click **Start server**, or tick **Start MCP server automatically** under **Tools > Preferences > AI Features > MCP Server**. The server listens on `http://127.0.0.1:42100/` (the port is configurable) and accepts local connections without credentials, so there is nothing to set up beyond registering it with your agent. If Tabular Editor 3 runs somewhere the machine is shared (a Remote Desktop or Citrix host, for instance), tick **Require access token** under **Tools > Preferences > AI Features > MCP Server**, and agents must then present the token the dialog shows. Administrators can enforce that by policy. The dialog provides ready-made registration configuration for each agent tool, which you paste once into the tool of your choice. A status bar indicator shows **MCP Started** or **MCP Stopped**, with the server address in its tooltip, and right-clicking it gives quick access to starting and stopping the server, copying a configuration and opening the preferences page.

**You decide up front what a connected agent may do.** The server dialog lets you set five permissions before the server starts, and any tool your grants do not cover is simply never offered to the agent:

- **Model metadata**: Deny, Read or Write *(default: Read)*
- **Model data**: Deny or Read *(default: Deny)*
- **Best Practice Analyzer**: Deny, Read or Write *(default: Read)*
- **Documents**: Deny, Read or Write *(default: Write)*
- **Macros**: Deny, Read or Write *(default: Write)*

Permissions are read when the server starts. If you change them while the server is running, stop and start it again for the change to take effect, and reconnect any agent that is already connected: an agent is handed its list of available tools when it connects, so until it reconnects it keeps working from the permissions that were in force at the time.

Granting **Model metadata > Write** lets an agent change your model through C# scripts that Tabular Editor compiles, safety-checks and executes atomically:

- All of a script's changes land as a single undo step, so one **Ctrl+Z** reverts everything it did.
- A script that fails part-way is rolled back completely, leaving no partial edits behind.
- The agent receives a structured summary of every change it made, along with any script output.
- Raw TMSL/XMLA execution is never available to an agent, and the DAX evaluation helpers work only when **Model data > Read** has been granted.
- A script that reaches outside the model (file access, web requests, assembly references) is never executed. Instead it opens as a C# script document for you to review and run yourself.

An agent can also be asked to *write* rather than run: with **Documents > Write**, it can place a C# script or a DAX query into a document in Tabular Editor for you to review and execute. Nothing is run on your behalf.

The same five permissions govern the **AI Assistant** chat, stored once and editable from either place: the server dialog, or **Tools > Preferences > AI Features > Permissions**. Whatever the grants do not cover, the chat continues to ask for with its usual consent card, and choosing **Always allow** there raises the standing grant. Permissions you have already granted to the chat carry over automatically. Use the built-in chat, your own agent, or both; they work from the same model and the same permissions.

The MCP server is enabled by default, can be turned off entirely in preferences, and administrators can disable it machine-wide by policy. It is available only when the AI Assistant module is part of the installation.

For details, see the new @mcp-server article, including [registering your agent](xref:mcp-server#register-your-agent), [deciding what the agent may do](xref:mcp-server#deciding-what-the-agent-may-do), [how an agent changes your model](xref:mcp-server#how-an-agent-changes-your-model) and [running on a shared machine](xref:mcp-server#running-on-a-shared-machine). The permission model is described in [Permissions and consent](xref:ai-assistant#permissions-and-consent), and the administrator controls in @policies.

### AI Assistant runs C# scripts directly

The **AI Assistant** can now carry out the model changes you ask for, instead of only writing a script for you to run. Tick **Allow AI assistant to run C# scripts directly** under **Tools > Preferences > AI Features > AI Assistant** to switch this on. It requires **Model metadata** to be set to **Write** under **Tools > Preferences > AI Features > Permissions**, and the checkbox stays unavailable until it is.

- Only scripts that Tabular Editor considers safe (those touching model objects and nothing else) run this way. Anything reaching for files, the network or external assemblies is still handed to you for review in a script document, and the assistant tells you why.
- Each run lands as a single undo step, so one **Ctrl+Z** reverts all of it, and a script that fails part-way leaves the model untouched.
- **Preview changes** is still honoured: with it turned on, you see the same preview of what the script changed before it stands, and choosing **Cancel** reverts everything and tells the assistant you did so.
- Asking for a script rather than for the change itself still opens it in a script editor tab for you to run yourself.

For details, see [Letting the assistant change your model](xref:ai-assistant#letting-the-assistant-change-your-model).

### Unsaved change indicators

Objects with unsaved changes are now marked throughout the editor, so you can see at a glance what you have touched since the last save.

In the **TOM Explorer**, an object is tinted and badged according to what happened to it:

- **Green** with a **+** badge: added since the last save
- **Red** with a **−** badge: deleted since the last save
- **Orange** with a dot badge: edited in place

A table, display folder or the **Model** node that is unchanged itself but holds a changed object somewhere beneath it shows the badge of what changed below, on a checkered fill in the same colour, so an unsaved change stays visible even while the branch holding it is collapsed. A new toolbar toggle filters the tree down to changed objects, keeping the containers needed to reach them. The **Properties** pane marks changed rows the same way and has a toggle of its own; while either filter is active, the pane title gains a **(Changed)** suffix. The indicators cover any unsaved change (made by hand, by a script, or by an AI agent) and clear the moment the model is saved, reloaded, or undone back to its last saved state.

**Putting individual changes back.** A marked row can be reverted on its own: right-click it in the **Properties** pane and choose **Revert** to restore just that property to its last saved value, leaving every other unsaved edit in place. Reverting behaves exactly like typing the old value back in: references in DAX are fixed up and dependent objects are recalculated, and a single **Edit > Undo** brings the edit back. With several objects selected, **Revert** puts the property back on all of them that changed it, as one undoable step.

Whole objects can be put back too. Right-click a marked object in the **TOM Explorer** (or its table, a display folder, or the **Model** node itself) and choose **Revert** to return it and everything beneath it to the way it was at the last save. Edited properties go back to their saved values, objects added since the save are removed, and objects deleted since the save come back exactly as they were, including a deleted measure's KPI or a deleted column's hierarchy levels and relationships, all as a single **Edit > Undo** step. Objects elsewhere in the model keep their unsaved changes, and anything that cannot be put back (for instance a deleted object whose name has since been taken by a new one) is listed in a message, while the rest of the revert stands.

**Deleted objects no longer simply vanish.** Until the model is saved they stay where they were in the **TOM Explorer**, struck through on the red deleted highlight, so a deletion is as easy to spot as an edit. Right-click one and choose **Restore** to bring it back exactly as it was the moment before it was deleted; any earlier edits come back with it and can be reverted separately. Struck-through rows cannot be edited, dragged or expanded, and selecting one does not select a model object.

**Preferences.** Under **Tools > Preferences > TOM Explorer > Unsaved changes** you can switch the object markers and the Properties pane markers off, gather a container's deleted objects under a single **Deleted objects** node instead of leaving each where it used to be, and decide how long deleted objects stay visible: never, until the model is saved (the default), or until the model is closed. The last option keeps objects deleted earlier in the session restorable, including objects that were created and deleted between two saves.

**For C# scripts.** `Revert()` on any object (or on a collection such as `Selected.Measures`, or on `Model` for everything) puts it and everything beneath it back to the saved state, and `Revert("Expression")` reverts a single property. `HasUnsavedChanges` tells you whether an object differs from the save, a container's `DeletedObjects` lists what it has lost in the session, and `Selected.Deleted` reaches the deleted objects selected in the tree. Each offers a `Restore()` method, so `Selected.Table.DeletedObjects.Restore()` brings back everything deleted from a table.

For details, see the new @unsaved-changes article, including [Reverting changes](xref:unsaved-changes#reverting-changes), [Deleted objects](xref:unsaved-changes#deleted-objects) and [Scripting](xref:unsaved-changes#scripting).

### Auto-reload from disk

Tabular Editor now notices when the model metadata files it loaded are changed outside the application (by an AI agent, a script, another editor, or a colleague) and brings those changes into the open model without you having to use **File > Reload from disk**. A model loaded from a `.bim` file watches that file; a model loaded from a folder watches every `.json` or `.tmdl` file below the model root.

- If you have no unsaved changes, the model is simply reloaded.
- If you do, an **External changes detected** prompt asks whether to **Reload** (discarding your local changes) or **Ignore** (keeping them). Dismissing the prompt keeps your changes.
- Changes that arrive while Tabular Editor is in the background are held and raised once when you return to it, and a burst of changes produces a single reload rather than one per file.
- In workspace mode a successful reload also redeploys the workspace database, so the two never drift apart.

The behaviour is enabled by default and can be turned off with the new **Automatically reload from disk (hot reload)** checkbox under **Tools > Preferences > Miscellaneous**.

For details, see the new @auto-reload article.

### Snowflake key pair authentication

Snowflake connections now support **key pair** authentication, in line with Snowflake's MFA enforcement roadmap for service accounts. In the Snowflake connection dialog, choose **Key pair** as the authenticator, enter your username, browse to your RSA private key file and, if the key is encrypted, enter its passphrase. Unencrypted PKCS#1/PKCS#8 keys and passphrase-encrypted PKCS#8 keys (the format produced by Snowflake's documented key-generation steps) are supported.

The key file path and its passphrase are saved with your connection settings, the passphrase encrypted so that only your Windows account can read it. Unlike browser-based authentication, key pair authentication needs no interactive sign-in, so a saved connection reconnects on its own, which makes it well suited to unattended use.

For details, see [Key pair authentication](xref:connect-snowflake#key-pair-authentication).

### Enterprise policies for the AI Assistant and MCP server

Administrators can now cap what the AI Assistant and the MCP server are allowed to reach, for each of the five resources separately: model metadata, model data (DAX query results), Best Practice Analyzer rules, open documents and macros. Where a limit applies, the matching option under **Tools > Preferences > AI Features > Permissions** and in the **Tools > MCP Server...** dialog only offers what is permitted, the assistant stops asking for permission it cannot be given, and nothing about the open model is shared when model metadata is off limits. The MCP server can be capped separately, and only downwards, so an unattended agent is never allowed more than the interactive chat.

The AI provider, the endpoint, the model or deployment name and the OpenAI organization and project can be locked the same way, or restricted to an allowlist of providers and endpoint hosts. Locked settings are read-only under **Tools > Preferences > AI Features > AI Assistant**, the AI Assistant uses the locked configuration whatever a user had chosen before, and a configuration the policy does not permit is refused with a message naming the rule that refused it, rather than quietly falling back to something else. Nothing is written into the user's own preferences, so their settings return if the policy is removed, and API keys are never distributed by policy.

Administrators can also publish a folder of Custom Instructions for everyone in the organization, and can rule out the ones a user keeps for themselves. Where an organization instruction and a user's own instruction share the same identifier, the organization's is the one that applies, and **Open Custom Instructions Folder** in the AI Assistant panel is unavailable while the user's own instructions are ruled out; the built-in instructions are unaffected either way. Finally, administrators can decide which tools the MCP server offers to connected agents (a tool withheld this way is still available to the AI Assistant itself) and can fix the server's **Port**, which then appears read-only under **Tools > Preferences > AI Features > MCP Server**.

These policies require Tabular Editor 3 Enterprise Edition. A copy that is not licensed for it does not ignore them: the AI Assistant and the MCP server refuse to start and say which values require the Enterprise Edition. To turn off AI functionality outright in any edition, the general `DisableAi` policy is unchanged.

For details, see [Enterprise policies](xref:policies#enterprise-policies) in the policies reference, and [Custom Instructions from your organization](xref:ai-assistant#custom-instructions-from-your-organization).

### Administrator policy for unsafe scripts

Administrators can now allow C# scripts and macros only where they stay within the semantic model. With the restriction in place, a script that reads or writes files, reaches the network, starts another program, pulls in outside code, or sends commands directly to the server is refused before it runs. This applies wherever a script runs: the script editor's **Run script** and **Run with preview** buttons, the Best Practice Analyzer's **Apply fix**, the **AI Assistant**, the **MCP server**, and the `te` command line. A macro that does any of those things no longer appears in any menu and is marked in **View > Macros**, where it can still be opened and edited.

This restriction requires Tabular Editor 3 Enterprise Edition: while the policy is set, any other edition will not allow script or macro execution at all.

For details, see [Administrator policies](xref:csharp-scripts#administrator-policies) in the C# scripts article, and [Scripts and macros](xref:policies#scripts-and-macros) in the policies reference.

### AI Assistant active model indicator

The **AI Assistant** panel now shows which AI model the assistant is using, in the status strip just above the message box alongside the context usage bar, so it is no longer necessary to open the preferences to tell one model from another. Clicking the model name opens a picker listing the models currently available for the configured provider, and choosing one applies it to every request that follows, with no dialog and no restart. The picker also offers a route to **Tools > Preferences > AI Features > AI Assistant** for a model that is not on the list.

Thank you to @edhans for giving this suggestion on our [GitHub ideas forum](https://github.com/TabularEditor/TabularEditor3/discussions/1580).

For details, see [Choosing a model](xref:ai-assistant#choosing-a-model).

### Per-file serialization for DAX UDFs

DAX User Defined Functions (UDFs) can now be serialized as individual files when saving a model with the JSON folder format. Each UDF is written to its own `.json` file under a `functions/` subfolder at the model root, so parallel edits to different UDFs no longer produce Git merge conflicts on the shared `database.json`. The new **User Defined Functions (UDFs)** toggle appears in **Tools > Preferences > Save-to-folder** and in **Model > Serialization Options**, and is enabled by default for new folder saves. Existing folder-serialized models keep their previous inline layout until you opt in via **Model > Serialization Options** and save.

For details, see [User Defined Functions (UDFs)](xref:save-to-folder#user-defined-functions-udfs) in the save-to-folder article, and @udfs.

### Semantic Analyzer flags user-context-aware calculated column limitations

The semantic analyzer now reports an error when a **user-context-aware calculated column** (a calculated column whose Expression Context is set to User Context) is referenced where Power BI does not allow it: from a standard calculated column or a calculated table, from a row-level security filter, or as a relationship endpoint, whether the reference is direct or reaches the column indirectly through a measure. Direct references are reported in the DAX editor, the **Messages** view and the `te validate` CLI command; indirect references and relationship-endpoint violations are reported in the **Messages** view.

For details, see @user-context-calculated-columns and @messages-view.

### Show actual DAX query in Data Preview

The **Data Preview** grid has a new **Show actual DAX query** right-click option. It opens a new, editable DAX Query document pre-populated with a query that reflects the preview's current filter and sort, so you can take the preview you are looking at and carry on working with it as a query.

For details, see [Show actual DAX query](xref:table-preview#show-actual-dax-query).

### Breaking change: C# scripts use the script query helpers instead of Model.Database

C# scripts can no longer call query/command members directly on `Model.Database`. The script-facing way to query the connected model is (and always was) the built-in script helpers `EvaluateDax(...)`, `ExecuteDax(...)`, `ExecuteReader(...)` and `ExecuteCommand(...)`, which are unchanged. Scripts that used the documented helpers are unaffected.

For details, see @script-helper-methods.

## Improvements in 3.27.0.0

- The **AI features** component is now selected by default in the Tabular Editor 3 installer, so the AI Assistant and the MCP server are available straight after a standard installation. Previously the component had to be ticked manually during setup, and anyone who accepted the defaults ended up without them. You can still untick it, and where your IT administrator has disabled AI features the component stays unavailable as before. See [Deploying without the AI features](xref:installation-activation-basic#deploying-without-the-ai-features).
- Tabular Editor 3 Enterprise Edition now keeps a record on your own computer of what the AI Assistant and the MCP server did: which permissions you were asked for and how you answered, which tools were used and whether each one succeeded, failed or was refused, and the full text of any C# script an agent ran or handed you for review. Prompts, replies and data values are never recorded. **Open audit folder**, on **Tools > Preferences > AI Features** and in the **Tools > MCP Server...** dialog, takes you to the daily files, which are kept for 30 days. Administrators can redirect the record to another folder, including a network share, and choose how long it is kept. See [Audit record](xref:ai-assistant#audit-record).
- Policies can now be set under `Software\Policies\Tabular Editor ApS`, with the product-specific subkeys `TE3` and `TECLI` for a policy that should reach one product only, and they are now read from the machine-wide hive as well, so Computer Configuration group policies apply and cannot be overridden by the user. The previous `Software\Policies\Kapacity\Tabular Editor` key keeps working unchanged, and the `te` command-line tool honors these policies on Windows. Tabular Editor 3 also installs a Group Policy administrative template pair, so every policy can be set from the Group Policy editor instead of by editing the registry. See @policies and [Using the administrative templates](xref:policies#using-the-administrative-templates).
- Improved the check that decides whether a C# script written by the **AI Assistant** can run without your review. Scripts that do things outside the model, such as saving files or sending commands to the server, are now consistently handed to you for review first, while scripts that only work with the model are no longer held back unnecessarily.
- A new **Color blindness mode** under **Tools > Preferences > User Interface > Accessibility** marks objects added since the last save in teal rather than green, so that added, deleted and changed objects stay distinct for the most common forms of color blindness. It covers the **TOM Explorer** change indicators and the colors of the model comparison view. See @accessibility.
- The context usage bar in the **AI Assistant** panel, and the point at which a conversation is automatically compacted, now reflect the real context window of the model in use rather than a single fixed figure applied to every model. The maximum length of a single reply is taken from the model as well, instead of being guessed from its name.
- The **AI Assistant** now decides which Custom Instructions apply to a request from each instruction's description, and an instruction it has picked up stays in effect for the rest of the conversation instead of only the message that brought it in. If you maintain your own instruction files, keep each file's `description` accurate and specific, since it is now what the assistant reads when choosing. The `triggers` section is ignored and can be removed; typing `/instruction-id` in the chat still loads an instruction explicitly. See [Custom Instructions](xref:ai-assistant#custom-instructions).
- The **AI model name** dropdown in **Tools > Preferences > AI Features > AI Assistant**, and the model picker in the **AI Assistant** panel, are now filled from a curated list of models maintained online and refreshed about once a day, with the recommended model for the provider listed first. New models become selectable without waiting for a Tabular Editor update, and models the provider has retired are no longer offered. Both remain free text, so any model name can still be typed by hand. See [Where the model list comes from](xref:ai-assistant#where-the-model-list-comes-from).
- Improved the responsiveness of the **AI Assistant** while a reply is streaming in. Previously, long replies rendered with increasing sluggishness and could make the chat window stutter as the response grew.
- The token statistics tooltip on the **AI Assistant**'s context usage indicator now separates what the latest exchange cost from the conversation's running totals, in three labelled sections: `Last turn`, `This conversation (billed)` and `Context`.
- When the **AI Provider** in **Tools > Preferences > AI Features > AI Assistant** is set to `Azure OpenAI`, the **Model name** field is now labelled **Deployment**, matching the term Azure OpenAI and Microsoft Foundry use for a model made available on your own resource. Only the label and its tooltip change.
- Added Power BI / Fabric compatibility level 1706 to the **New Model** dialog, replacing 1702 as the latest level. 1706 is now treated as the latest level throughout the application, including the "Power BI models should use latest compatibility level" Best Practice Analyzer rule and new Power BI models created with `te init`.
- The **Data Preview** values filter is limited to 5,000 distinct rows. A new preference lets you raise that limit if you work with large tables, but bear in mind that raising it can increase loading times.
- Added a **Sort table preview columns alphabetically** preference under **Tools > Preferences > Data Browsing > Table Preview**. When enabled, **Data Preview** columns are sorted by name, matching the order the **TOM Explorer** lists them in rather than the order the engine returns. Off by default. See [Column order](xref:table-preview#column-order).

Tracking is on by default and can be turned off for an individual preview via the **Track selected column** toolbar button, or globally under **Tools > Preferences > Data Browsing > Table Preview > Behavior**. - Metric View objects can now be renamed directly, without having to create a new object and delete the old one. ## Bugfixes in 3.27.0.0

- Fixed an issue where saving a model in TMDL format could destroy a table, role, perspective or culture whose file name differed from the object's own name only by letter case, for example a table named `Sales` held in `tables/sales.tmdl`, which is what renaming an object leaves behind. Previously the save reported success, but the object's file was deleted along with everything in it, and the object was simply missing the next time the model was opened. Such a model now saves correctly: the object survives, its file is kept under the object's own name, and the edit that prompted the save is applied.
- Fixed an issue where columns could be created in an arbitrary order when importing or updating a table from a SQL Server, Fabric Lakehouse or Fabric Warehouse source, in both **Model > Import Tables** and **Model > Update Table Schema** as well as in the CLI. Columns now follow the column order of the source table.
- Fixed an issue where importing a table from a Fabric Lakehouse or Warehouse through a data source that already carried its SQL analytics endpoint could silently create a table with no columns. A clear error is now shown when no columns are available.
- Fixed an issue where importing a table whose server, database, schema or object name contains a double quote produced a Power Query expression that would not parse. Such names, and the query itself when importing from Databricks or Snowflake, are now escaped correctly.
- Fixed an issue where a Snowflake connection using **External browser** authentication could not recover once its cached sign-in expired or was revoked by the identity provider. Previously, every subsequent Snowflake operation failed without reopening the browser, the Import Table wizard silently showed empty tables and columns instead of an error, and the only way to recover was to restart Tabular Editor. The browser sign-in now reopens as soon as Snowflake rejects the cached one, and a sign-in that times out or is abandoned is treated as a cancellation rather than an error that blocks later operations. See [External browser sign-ins](xref:connect-snowflake#external-browser-sign-ins).
- Fixed an issue where saving a model to a folder or a `.bim` file on macOS or Linux produced different files than on Windows, including object names that could not be checked out on Windows, platform-dependent line endings and a varying table order. Models saved on any platform now produce identical output. This also fixes a long-standing issue where two objects whose names map to the same escaped file name would overwrite each other's file.
- Fixed an issue where moving a measure or calculated column to another table, or duplicating it, made its error indicator disappear even though the expression was still invalid. Previously, the indicator only came back after the expression was edited again.
- Fixed an issue where the **TOM Explorer** collapsed and lost the current selection when a model with a workspace database connected was reloaded, either through **File > Reload from disk** or through an automatic reload after the files changed on disk. The expanded nodes, focused object, selection and scroll position are now kept, and reloading a model opened from a file keeps the selection as well.
- Fixed an issue where pasting an object in the **TOM Explorer** could leave both the original and the pasted copy selected, with the tree scrolled away from the pasted object. The pasted object is now selected, focused and kept in view.
- Fixed an issue where selecting an object in the **TOM Explorer** while working in another view could switch the active document to an open model diagram.
- Fixed an issue where selecting a Direct Lake partition, or a partition generated by an incremental refresh policy, in the **TOM Explorer** raised an error and opened the crash report dialog. The **Expression Editor** now shows the partition's data coverage definition expression if it has one, and stays empty otherwise.
- Fixed an issue where opening a model containing calculated tables whose columns are inferred from the DAX expression could intermittently fail with a "Collection was modified; enumeration operation may not execute" error.
- Opening a model no longer fails with an error when the model's user options file (`.tmuo`) holds no readable content. The file is now also written atomically, so an interrupted write cannot damage it in the first place.
- Fixed an issue where saving a PBIP semantic model authored by Power BI Desktop renamed the item and cleared any description set in Fabric, which then propagated to the workspace on the next Fabric git sync. Saving such a model to a new location now also names the folder after the item.
- Fixed an issue where **File > Save As...** could suggest a file name that Windows refuses to save, most commonly for a document whose tab caption contains a colon. Invalid characters are now percent-encoded in the suggested name, which remains fully editable.
- Fixed an issue where the text in the status bar could be unreadable when a custom **Status bar color** was picked for a connection. The status bar text and link colors are now derived from the chosen color rather than from the active theme.
- Fixed an issue where the Best Practice Analyzer's "Rules for the local user" collection could appear read-only on a machine where Tabular Editor had not yet created its local application data folder, such as on first run.
- Fixed DAX auto-complete suggesting user-defined functions that are not valid in the current argument context and omitting valid ones. UDFs are now filtered by their inferred return type, filter arguments suggest UDFs (they were previously omitted entirely), and UDFs whose definition contains a semantic error are no longer offered.
- Fixed an issue where **Inline measure** in the DAX editor could silently change the result of a calculation when the reference was inside a row context, for example inside `SUMX` or `FILTER`. The inlined expression is now wrapped in `CALCULATE( ... )` to preserve the context transition a measure reference performs, but only where that wrap can make a difference.
- Fixed an issue where **Inline measure** could comment out part of the surrounding expression when the expanded measure's expression ends with a comment line. Whatever followed the measure reference on that line is now moved to a new line, indented to match.
- Fixed an issue where the **AI Assistant** in the portable (zip) edition was sometimes unavailable after launch even though an AI provider was already configured. Previously, sending a message reported "AI client not initialized", and confirming the unchanged settings then failed with a "Method not found" error that persisted until the application was restarted. The assistant now initializes consistently on every launch, and whenever initialization does fail, the chat reports the actual reason.
- Fixed an issue where the **AI Assistant** failed to initialize when the provider was set to `Anthropic` or `OpenAI` with the model name left blank. A blank model name now works as intended, and initialization failures are reported in the chat instead of nothing happening.
- Fixed an issue where the **AI Assistant** could fail with the error "The requested operation requires an element of type 'Number', but the target element has type 'String'" when asked to revise a script or query it had written earlier in the conversation. The reply is now completed and the existing script or query is updated in place.
- Fixed an issue where the **Stop** button in the **AI Assistant** did nothing while a **Permission Required** card was waiting for an answer, leaving the conversation stuck. Pressing **Stop** now ends the turn, and the same conversation can be continued with a new message.
- Fixed an issue where code blocks in the **AI Assistant** were unreadable under a light theme, appearing as near-black text on a near-black block. Code blocks, their language label, **Copy** button and syntax coloring now follow the theme, and the block's header strip has been tidied up.
- Fixed an issue where the **Delete conversation** button on the **AI Assistant** toolbar deleted the current conversation immediately, with no way to get it back. It now asks for confirmation, and has moved away from the panel's close button, where it was easily mistaken for it.
- Fixed an issue where the text directly following a script or query card in an **AI Assistant** reply could appear unformatted, showing raw characters such as `**` or backticks instead of formatted text.
- Fixed an issue where the **AI Assistant** could create a duplicate object instead of updating an existing one, when that object had been renamed, moved or edited after the assistant first created it. Long conversations with Anthropic models are also noticeably faster and cheaper.
- Fixed the **AI Assistant** showing an error and failing to respond when connected to a custom (OpenAI-compatible) provider using certain thinking/reasoning models. Requests that rely on tools, such as listing measures or running a DAX query, now work with these models.
